# TriageOS · 急诊分诊决策中枢

> 一个**可以直接跑**的急诊分诊原型：6 个核心 Agent + 2 个底座。
> 患者用大白话描述症状，系统在几十毫秒内完成「采集 → 排雷 → 定级 → 质控 → 监测 → 沟通」，
> 高危或 Agent 之间吵架时，自动把工单推给真人医生。

```bash
cd triage_ed
python run.py
```

打开 <http://127.0.0.1:8770>。零依赖：只用 Python 3.10+ 标准库（二维码组件已 vendored 进仓库，断网可用）。

> ⚠️ **这是演示原型**：医学规则按急诊通行诊疗路径整理，用于流程与规则演练，
> **不构成临床决策依据，不用于真实诊疗**。所有"分级"都必须由有资质的医生最终确认。

## 一、三个界面，对应三种角色

| 界面 | 地址 | 谁用 | 干什么 |
|---|---|---|---|
| 分诊工作台 | `/` | 分诊护士 | 录主诉（原话即可）→ 看 6 个 Agent 的决策链 → 打印/展示患者二维码 |
| 患者扫码页 | `/h5?t=<token>` | 患者/家属 | 看排到第几位、要等多久；点「更痛了」立刻触发重新评估 |
| 医生接管台 | `/doctor` | 值班医生 | 收 P0/P1 工单，看两边 Agent 的意见，做最终裁决并留痕 |

手机扫码需要电脑和手机在同一 Wi-Fi：

```bash
python run.py --lan        # 二维码自动指向局域网 IP
```

  底座 1  医学术语语义库（terminology.py）  ── 54 个术语 × 329 条口语变体 + 21 项化验

**关键设计原则：Agent 可以自动升级，绝不自动降级。** 降级只能由人做，且必须写理由。

## 三、六个 Agent 的契约

| # | Agent | 人设 | 输入 | 输出（结构化） | 失败模式 |
|---|---|---|---|---|---|
| ① | 信息采集与多模态 | 极其敏锐的护士 | 主诉原话、生命体征、既往史、化验单文本 | `translation[]`（原话→术语）、`labs[]`（含危急值）、`missing[]` | 主诉太短 → 输出补问清单 |
| ② | 红旗风险预警 | 极其博学的急诊老专家 | ①的结构化结果 | `flags[]`（病名/为什么致命/时间窗/证据/追问/下一步）、`cleared[]`、`partial[]` | 单条规则异常被隔离，不拖垮流水线 |
| ③ | 分级裁判 | 极其冷酷的台长 | ②的结果 + 生命体征 | ESI 级别、四步法依据、资源项、目标候诊时间 | 证据不足 → 置信度下降并在卡片上标注 |
| ④ | 交叉核验质控 | 极其严苛的质控主任 | ①的结构化事实 + ③的级别 | 安全底线、8 项检查、最终级别、两派意见 | 发现低判 → 自动升级并弹 P0 工单 |
| ⑤ | 动态候诊监测 | 极其尽责的巡视员 | 队列 + H5 上报 | 复评间隔、位次、升级判定、超时提醒 | 上报后重跑②③④，只升不降 |
| ⑥ | 医患沟通安抚 | 极高情商的外交官 | 队列构成 + 情绪 | 三版话术、禁忌清单、红线提示 | 不承诺"马上看"、不评价其他患者 |

每个 Agent 的输出都带：`status`（完成/需注意/高危/监测中）、`headline`、`points[]`、`confidence`、`elapsed_ms`，
所以界面上每张卡片都能点开看"它凭什么这么判"。

## 四、底座 1：医学术语语义库

`app/terminology.py` 干四件事：

1. **口语 → 术语**：`胸口像被刀割一样疼` → `撕裂样胸痛`
   （词典 + 部位/修饰正则兜底，长词优先，同一段文字不会被重复吃掉）
2. **否定识别**：`没有胸痛` 不算胸痛；但 `胸痛持续不缓解` 不能因为前面有个"不"就漏掉
3. **生命体征抽取**：`血压 88/54，心率 122，血氧 91%` → 结构化，并按红/黄分级
4. **旧化验单解析**：`肌钙蛋白I 0.82 ng/mL ↑` → 项目/数值/单位/参考区间/危急值判定

规模：54 个症状术语、329 条口语变体、21 个既往史/危险因素、10 类性状修饰、21 项化验（含危急值阈值）。

## 五、底座 2：Human-in-the-loop

触发条件（自动开单）：

| 工单类型 | 优先级 | SLA | 触发场景 |
|---|---|---|---|
| `red_flag` | P0 | 5 分钟 | 致命病红旗 / ESI 1 级 |
| `conflict` | P0 | 5 分钟 | Agent ③ 与 ④ 分级不一致 |
| `deterioration` | P0 | 5 分钟 | 候诊期间 H5 上报导致升级 |
| `missing_info` | P1 | 15 分钟 | 关键证据缺口（如育龄女性未查 β-hCG） |
| `nurse_call` | P1 | 10 分钟 | 护士站手动呼叫 |
| `recheck_overdue` | P2 | 30 分钟 | 复评超时（Agent ⑤ 巡视发现） |

医生可以：同意分级 / 升级 / 降级（必须写理由）/ 要求补信息 / **接管该患者**。
一旦接管，该患者的 Agent 决策全部冻结（`/api/report` 会返回"已由医生接管"），
所有人工动作进审计日志，`/doctor` 底部的表格可以查。

## 六、关于 ESI 的 1–4 级 vs 1–5 级

需求里写的是"按 ESI 标准打分（1–4 级）"，但 **ESI v4 标准本身是 1–5 级**：

- 1 级 = 需要立即抢救性干预
- 2 级 = 高危 / 剧痛 / 意识改变
- 3 级 = 预计≥2 项资源
- 4 级 = 预计 1 项资源
- 5 级 = 不需要资源

这个原型**同时给出两套数字**：引擎按标准五级制计算，界面上标 `ESI 3`，
并在旁边给出"简化四级制 = 3"。5 级在四级制里并入 4 级（都属于"候诊"）。

如果汇报时只想讲四级制，启动时加 `--esi 4`，界面会以四级制为主。

## 七、18 条致命病规则

| 病种 | 主要触发线索 | 为什么致命 | 时间窗 |
|---|---|---|---|
| 急性冠脉综合征 | 压榨样胸痛 + 大汗/放射 + 危险因素 | 室颤、心源性休克 | 进门到球囊 ≤90 分钟 |
| 主动脉夹层 | 撕裂样/刀割样 + 胸背痛 + 高血压/马凡 | 破裂即失血性休克 | 48 小时内每小时死亡率约 1% |
| 肺栓塞 | 呼吸困难 + 制动/手术/肿瘤/单侧腿肿 | 右心衰、梗阻性休克 | 小时级 |
| 急性脑卒中 | 偏瘫/失语/口角歪斜/视力障碍 | 每分钟 190 万神经元死亡 | 溶栓 4.5h，取栓 6–24h |
| 蛛网膜下腔出血 | 雷击样头痛 + 颈强直/呕吐 | 再出血死亡率 50%–80% | 6 小时内 CT，阴性腰穿 |
| 异位妊娠破裂 | 育龄女性 + 停经 + 腹痛/出血/晕厥 | 腹腔内大出血 | 边复苏边手术 |
| 脓毒症/感染性休克 | 发热 + 低血压/呼吸快/意识改变 + 乳酸 | 病死率 30%–50% | 1 小时集束化治疗 |
| 过敏性休克 | 皮疹 + 呼吸困难 + 低血压 | 喉头水肿 | 分钟级 |
| 上消化道大出血 | 呕血/黑便 + 休克征象 | 失血性休克、误吸 | 24 小时内急诊内镜 |
| 急性气道梗阻/会厌炎 | 流涎/吞咽困难 + 喘鸣 | 完全梗阻 | 分钟级 |
| 颅内感染 | 发热 + 颈强直 + 瘀点/意识改变 | 暴发型 24 小时进展 | 1 小时内抗生素 |
| 低血糖/代谢性脑病 | 意识改变 + 糖尿病/血糖低 | 不可逆脑损伤 | 分钟级 |
| 恶性心律失常/心源性晕厥 | 晕厥 + 心悸 + 心脏病史 | 随时室颤 | 持续监护 |
| 肠系膜缺血/绞窄 | 腹痛 + 房颤/停止排气排便 + 乳酸 | 肠坏死穿孔 | 黄金 6 小时 |
| 睾丸扭转 | 睾丸疼痛/肿胀 + 恶心 | 睾丸坏死 | 黄金 6 小时 |
| 糖尿病酮症酸中毒 | 多饮多尿 + 呕吐/腹痛 + 血糖高 | 酸中毒、低钾 | 小时级 |
| 老年急腹症 | ≥65 岁腹痛（症状体征分离） | 发现即晚期 | 黄金 6 小时 |
| 小婴儿发热 | ≤3 月龄 + 发热 | 严重细菌感染唯一表现 | 分钟级评估 |

再加上质控的 8 项交叉检查（红旗漏判、危重生命体征漏判、剧痛与级别矛盾、生命体征缺口、
人口学缺口、育龄女性未查 hCG、过敏史缺失、过度分级），构成"防漏诊"的两道网。

## 八、7 分钟演示剧本

| 场景 | 操作 | 想让人看到什么 |
|---|---|---|
| ① 排雷 | 点「① 撕裂样胸背痛」 | 夹层 + 心梗双预警，卡片里直接给出"为什么致命/追问清单/下一步"，ESI 2 级 |
| ② 化验单 | 点「② 压榨性胸痛」 | 肌钙蛋白 0.82 被判**危急值**并置顶；左侧"旧化验单"框可以直接粘贴文字 |
| ③ 质控卡漏 | 点「③ 停经 45 天」 | 宫外孕预警 + **质控卡住"未查 hCG"**，同时给出 P0 + P1 两张工单 |
| ④ 休克 | 点「④ 高热 + 叫不醒」 | 直接 ESI 1 级，P0 立刻弹到接管台 |
| ⑤ 卒中 | 点「⑤ 说话不清」 | 追问清单里有"最后一次正常时间"，体现卒中通道的要点 |
| ⑥ 不给高分 | 点「⑦ 切菜划伤」 | ESI 4 级 + 安抚话术，说明"不乱升级"同样是能力 |
| ⑦ 扫码升级 | 跑完⑥后点「模拟扫码上报」→ 在 H5 里点「更痛了」拉满 10 分 | 分级 4→2，队列前移，P0 工单进接管台 |
| ⑧ 人来兜底 | 打开 `/doctor` | 看到两派意见并列、超时红标、降级必须写理由、审计流水 |

演示前建议：先点「填充候诊队列」，这样沟通 Agent 的话术里会出现
"前面还有 2 位最高级别的危重患者（急性冠脉综合征、急性脑卒中）"——这就是对外解释的底气。

## 十二、设计取舍

**为什么不用大模型当主引擎？** 急诊分级要的是可解释、可复现、毫秒级、断网可用。
确定性规则引擎在演示和科室评审里更站得住脚：每一条结论都能点开看到证据。
大模型更适合放在"话术改写""病历摘要"这类不承担安全责任的位置
（`comms.py` 已经预留了接口，配置 `DEEPSEEK_API_KEY` 也不会影响现有逻辑）。

**为什么质控要独立重算而不是复查？** 复查容易被同一个思维惯性带偏。
这里用的是"安全底线"——任何致命红旗都不允许判到 3 级及以下，跟裁判怎么想无关。

**为什么 Agent 不能自动降级？** 自动降级一旦错一次就是人命。升级错了只是浪费一张床，
降级错了是不可逆的。宁可让医生多点一次鼠标。

## 十三、已知限制

- 演示数据放在 JSON 文件里，没做并发写入的数据库级事务（单进程演示够用）
- 不做真实 OCR：化验单以"粘贴文本"为主；图片上传只做归档（真实项目应接 OCR + 结构化）
- 队列位次按"级别 + 疼痛 + 到达时间"排序，没有考虑检查往返、床位占用等真实因素
- ESI 第 3 步的资源预测来自症状映射表，真实场景应由医生在系统中勾选
